## 7. Key design decisions for Phase 3 planning

1. **Where does ChargeStore live?** Options: new file in `@manta/bus` (co-located with other state stores), or standalone `@manta/charges` package. Bus is the natural home since charges persist in `.manta/state/` alongside registry/contracts/casts.

2. **Persistence: sqlite vs JSON+lockfile.** Spec mandates forking-realities investigation. JSON+lockfile is consistent with existing bus stores (registry.ts, locks.ts, etc. all use `atomicMutateJson`). SQLite would be a new dependency.

3. **Outcome classification.** `death_reason` strings are currently freeform. Phase 3 needs a deterministic `success | fail | neutral` classifier. Options: structured `death_reason` enum, or separate `cast_outcome` field on CastManifest.

4. **Passive recovery timer.** The orchestrator currently only runs during active casts (tick-loop). Idle recovery needs either: (a) a daemon process, (b) a startup-time catch-up calculation (idle_minutes × rate, capped), or (c) on-demand recalc when `/manta cast` reads `charges.json`.

5. **Daily cap.** Needs wall-clock date tracking. Current bus has no date/session concept — only epoch timestamps on registry records.

6. **Token counting.** `Budget.tokensUsed` / `dollarsUsed` are placeholders. Actual token counting requires either Claude API cost reporting (not available via `--print` mode) or estimation from snapshot size + expected turns.
